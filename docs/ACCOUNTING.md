# 记账规则、幂等与结算/对账语义

## 1. 会计模型

系统是**单一法人账簿**（支付机构/电子钱包运营方视角）。用户钱包余额是运营方对用户的**负债**，
用户充值对应的资金是运营方的**备付金资产**。所有资金运动都以**复式记账凭证**记录，
每张凭证必须借贷平衡。

### 1.1 账户类型与正常余额方向

| 类型 | 正常余额方向 | 例子 |
| --- | --- | --- |
| ASSET 资产 | 借方 | `FLOAT_CASH`（备付金）、`RECON_SUSPENSE_REC`（对账暂记应收） |
| LIABILITY 负债 | 贷方 | 用户/商户钱包、`PAYABLE_MERCHANT:<商户>`（待结算款）、`RECON_SUSPENSE`（暂记应付） |
| INCOME 收入 | 贷方 | `FEE_INCOME`（手续费收入） |
| EXPENSE 费用 | 借方 | （预留） |
| EQUITY 权益 | 贷方 | （预留） |

账户余额始终保存为**正常余额方向上的非负净值**。过账时的余额约束：

- 借方正常账户：本凭证的**贷方发生额** ≤ 当前余额；
- 贷方正常账户：本凭证的**借方发生额** ≤ 当前余额。

这比"余额不能出现反方向"更通用：既阻止资产/钱包透支，也允许负债账户之间合法的
"借 A 贷 B"划转（如两个钱包间转账：借 转出方钱包 / 贷 转入方钱包）。

### 1.2 业务分录

**入金（充值）** `INITIAL_DEPOSIT`

```
借 FLOAT_CASH            （备付金资产增加）
  贷 <用户钱包>           （钱包负债增加）
```

**支付受理** `PAYMENT`（资金不直接进商户钱包，先进待结算负债）

```
借 <付款方钱包>           （负债减少）
  贷 PAYABLE_MERCHANT:<商户> （待结算负债增加）
```

**批次结算** `SETTLEMENT`（待结算款结入商户钱包，按商户汇总成一张凭证）

```
借 PAYABLE_MERCHANT:<商户A>  （待结算负债减少）
  贷 <商户A钱包>             （商户负债增加）
借 PAYABLE_MERCHANT:<商户B>
  贷 <商户B钱包>
  ...
```

**批次手续费** `SETTLEMENT_FEE`（独立凭证，逐商户扣收，贷记手续费收入）

```
借 <商户A钱包>  feeA
借 <商户B钱包>  feeB
  贷 FEE_INCOME  feeA + feeB
```

手续费口径：`fee_i = floor(amount_i × BPS / 10000)`，**逐笔计算后汇总**
（默认 BPS=60，即 0.60%）。批次毛额、手续费、净额在建批时固定；
结算时按"支付额 − 结算前已退额"的实际口径重新计提（见第 4 节）。

**退款** `REFUND`（按原支付当前账上状态选择资金来源，两种形态）

```
未结算（含已进待结算批次）：          已结算：
借 PAYABLE_MERCHANT:<商户>            借 <商户钱包>
  贷 <付款方钱包>                       贷 <付款方钱包>
```

未结算时钱还在商户待结算负债里，退款直接冲减该负债，后续结算只会结
"支付额 − 已退额"；已结算时钱已在商户钱包，退款从商户钱包扣回，
商户钱包余额不足则整笔退款失败（`INSUFFICIENT_FUNDS`），一分钱不动。

**对账自动调整** `RECON_ADJUSTMENT`（见第 5 节）。

### 1.3 原子性

- 所有写操作通过 `storage.Store.Update(func(tx *Tx) error)` 在**同一个互斥临界区**内完成；
  回滚模型：进入临界区前对全部 map 做浅快照，回调返回错误时整体恢复
  （存储层保存的都是"先复制再写入"的不可变对象，浅快照即足够），
  因此任何一笔业务要么整笔落账、要么一分钱都不动。
- 支付受理/退款在同一临界区内完成"幂等记录写入 + 凭证过账 + 单据写入 + 幂等记录置 DONE"，
  因此不可能出现只扣款不入账的半截状态。
- 凭证按业务键 `(BizType, BizID)` 唯一：`postInTx` 发现重复业务键时直接返回原凭证，
  这是记账引擎自身的第二道幂等防线。

## 2. 支付受理与幂等语义

幂等记录三状态：`IN_FLIGHT` → `DONE` / `FAILED`，记录请求指纹
`(付款方, 收款方, 金额, 币种, 附言)` 与业务种类（`PAYMENT` / `REFUND`，不同种类的键不能混用）。

| 到达情形 | 处理 |
| --- | --- |
| 无记录 | 写入 IN_FLIGHT → 原子过账与建支付单 → 置 DONE，返回新支付单 |
| 有 DONE 记录且**指纹相同** | 直接返回首次支付单，`Replayed=true`，**不过账、不扣款** |
| 有 FAILED 记录且**指纹相同** | 返回**与首次完全相同的失败结论**（同错误码、同原因说明） |
| 有 DONE/FAILED/IN_FLIGHT 记录且**指纹不同**（或业务种类不同） | 返回 `IDEMPOTENCY_CONFLICT`，明确拒绝（错误信息携带既有内容与本次内容） |
| 相同键**并发**到达 | 临界区串行化：胜者完成受理；败者看到 IN_FLIGHT，返回 `IDEMPOTENCY_CONFLICT`，调用方稍后以**相同请求**重试即可拿到幂等结果 |

设计要点：

- 幂等键必填；缺键、金额非正、同账户收付等参数问题返回 `INVALID_ARGUMENT`；
- 账户不存在 / 币种不一致 / 余额不足分别返回 `ACCOUNT_NOT_FOUND` /
  `CURRENCY_MISMATCH` / `INSUFFICIENT_FUNDS`，失败原因可区分；
- **失败语义**：因"说得清的原因"失败的请求，失败结论（错误码 + 原因说明）按幂等键
  落档为 FAILED 记录并提交（不落账、不动余额）。之后同键同内容重试得到**稳定且同因**
  的失败结论，不会出现"标识被永久占住、只回一个含糊的处理中/冲突"；同键不同内容仍按
  冲突拒绝；换一个新的幂等键可正常重新发起；
- 失败受理不会产生凭证，账户余额与试算平衡保持不变。

## 3. 退款语义

退款针对**已受理成功**的支付发起，支持全额或多次部分退款；每笔退款有独立幂等键，
指纹为 `(原支付号, 金额, 币种, 原因)`，幂等与失败语义与第 2 节完全一致
（重复提交重放原退款单、同键不同内容冲突、失败结论落档稳定重放）。

### 3.1 可退上限与并发

- 支付单上累计记录 `RefundedAmount`，剩余可退 = 支付金额 − 已退金额；
  超过剩余可退返回 `REFUND_EXCEEDS_REMAINING`；
- 多次部分退款与并发退款都在同一存储临界区内串行化判定与落账：
  不超退、不丢更新，任意时刻剩余可退金额都是准确的。

### 3.2 退款资金来源（与支付账上状态对齐）

| 原支付状态 | 退款分录 | 说明 |
| --- | --- | --- |
| `PENDING_SETTLEMENT`（含已进待结算批次） | 借 `PAYABLE_MERCHANT:<商户>` / 贷 付款方钱包 | 钱还在待结算负债，直接冲减 |
| `SETTLED` | 借 商户钱包 / 贷 付款方钱包 | 钱已结给商户，从商户钱包扣回；余额不足则 `INSUFFICIENT_FUNDS` |

退款凭证、支付单累计退款额、退款单、幂等记录在同一原子临界区内落库：
要么整笔落到账上，要么一分钱都不动。

### 3.3 退款与结算/对账的先后关系

- **先退款后结算**（含支付已进待结算批次）：结算口径自动变为
  `实际结算额 = 支付额 − 已退额`，手续费按实际结算额逐笔计提；
  已退还给用户的钱不会再结给商户。全额退款的支付实际结算额为 0，
  不参与结算凭证，但仍随批次置为 `SETTLED`；
- **先结算后退款**：从商户钱包退回，不影响已完成的结算批次；
- **退款后对账**：对账的内部期望口径为支付的实际结算额（`SettledAmount`），
  对账单中按**退款号**出现的记录会被识别为已知退款并参与匹配，
  不会被误判为"内部缺失"的单边差异或重复记录；退款金额不符只登记人工核查，
  不自动调整客户账；全额退款（实际结算额 0）的支付不要求出现在对账单中；
- **兼容范围**：重复结算、重复对账、重复退款均幂等，不重复记账、不多出调整凭证；
  退款只改变"之后"的结算与对账口径，不回改已完成的结算批次与对账运行结果。

## 4. 结算语义

1. **建批 `CreateBatch`**：批次单一币种；所有支付必须存在、币种一致、状态为
   `PENDING_SETTLEMENT` 且未归属过批次（防止重复打包）。批次保存毛额、手续费、
   净额与支付清单，并把支付的 `SettlementBatchID` 指向批次。
2. **结算 `SettleBatch`**：在一个临界区内过"结算凭证 + 手续费凭证"两张平衡凭证，
   随后批次置 `SETTLED`、批次内支付全部置 `SETTLED`。任一步失败整体回滚。
   **口径跟随退款**：每笔支付实际结算额 = 支付金额 − 结算前已累计退款额，
   手续费按实际结算额逐笔计提；批次另存 `SettledGross/SettledFee/SettledNet`
   记录实际过账口径，支付单记录各自 `SettledAmount` 供对账使用。
   全额退款的支付实际结算额为 0，不出现在结算凭证中。
3. **结算幂等**：对已 `SETTLED` 批次再次调用，直接返回既有批次，不重复过账、不重复扣费。

商户最终到账净额 = 实际结算毛额 − 手续费；结算后其 `PAYABLE_MERCHANT` 账户余额归零。

## 5. 对账语义

输入：已结算批次 + 对账单记录（`TxnID` 对齐内部支付号或退款号；来源可为内存构造或
本地 CSV，无网络依赖）。内部期望口径：支付按**实际结算额**（`SettledAmount`），
退款按退款金额；实际结算额为 0（结算前已全额退款）的支付不要求出现在对账单中。
对账单中 `TxnID` 命中本批次支付关联退款号的记录被识别为**退款记录**：金额一致即匹配，
金额不符只登记人工核查（不自动调整），绝不会被误判为"内部缺失"或重复记录。

### 5.1 差异分类

| 差异类型 | 判定 | 处理 |
| --- | --- | --- |
| `MISSING_IN_STATEMENT` | 内部有已结算交易，对账单完全没有 | **不自动调整**，登记差异挂人工核查 |
| `MISSING_IN_INTERNAL` | 对账单有 `TxnID`，内部无此交易 | 自动调整：借 FLOAT_CASH / 贷 RECON_SUSPENSE（应付暂记） |
| `AMOUNT_MISMATCH` | 双方都有但金额不等 | 按差额自动调整（见下） |
| `DUPLICATE_RECORD` | 对账单中同一 `TxnID` 出现多次 | 第一条参与匹配，多出的条目登记为重复，**不自动调整** |

金额不符的差额调整（`delta = 对账单金额 − 内部金额`）：

```
delta > 0（渠道多收）：借 FLOAT_CASH delta / 贷 RECON_SUSPENSE delta
delta < 0（渠道少收）：借 RECON_SUSPENSE_REC |delta| / 贷 FLOAT_CASH |delta|
```

使用**两个方向不同的暂记科目**（负债/资产），保证自动调整凭证本身也满足
"账户余额不得为负"的约束。自动调整只触碰系统科目（备付金、暂记），
**不直接改客户与商户账**；单边缺失（对账单侧）与重复记录只登记不调整，留给人工。

### 5.2 对账幂等

对账结果以 `BatchID` 为键持久化。对同一批次再次执行 `Reconcile` 时**直接返回首次运行
结果**，不会重新匹配、不会生成第二张调整凭证、暂记科目余额不变。
调整凭证的业务键为 `RECON:<TxnID>:MISMATCH` / `RECON:<TxnID>:MISSING_INTERNAL`，
即使绕过批次幂等也会被记账引擎的业务键唯一约束挡住。

## 6. 并发与一致性说明

- 内存存储用一把互斥锁把每个 `Update` 临界区串行化，等价于数据库的可串行化事务；
  `View` 提供一致读。生产环境替换为数据库时，对应到行锁/乐观版本号
  （账户上有 `Version` 字段）即可，领域语义不变。
- 并发划转测试验证两件事：高并发下（1）总成功笔数与双方余额严格守恒、不丢更新；
  （2）余额只够部分请求时成功笔数恰为 `初始余额/单笔金额`，余额绝不为负。
- 并发退款测试验证：同一笔支付上 20 个并发退款请求（各 500，原额 2500）恰成功 5 笔、
  其余以 `REFUND_EXCEEDS_REMAINING` 拒绝，累计退款严格等于成功笔数 × 单笔金额，
  不超退、不丢更新。

## 7. 验证方法

```bash
go test -race -count=3 ./...      # 全量、竞态检测、重复 3 次
go run ./cmd/demo                 # 端到端演示
```

测试日志会打印幂等键/交易号以及判定依据，例如：

- `幂等键 key-replay 判定依据: 三次提交均返回支付号 pay-...，余额保持 ...（仅扣一次）`
- `交易号 tx-nsf 判定依据: 余额 100 < 需扣减 101, 错误码 ErrInsufficientFunds`
- `幂等键 key-nsf 判定依据: 两次提交均稳定返回 INSUFFICIENT_FUNDS（...），标识未被永久占住为含糊冲突`
- `支付号 pay-... 判定依据: 20 个并发请求各退 500，成功 5 笔，超退拒绝 15 笔，累计已退 2500 未超原额 2500`
- `批次 batch-... 判定依据: 实际结算毛额 4500（原毛额 6500 − 已退 2000），商户到账 4473，待结算款 0`
- `批次 batch-... 对账判定依据: 内部 3 笔 + 退款 2 条，对账单 4 条全部匹配（含退款号 ref-.../ref-...），差异 0`
- `批次 batch-... 重复对账判定依据: 复用首次运行结果，调整凭证仍为 jrn-...，暂记余额保持 ...`

每个正常路径用例结束时都做试算平衡断言（借方合计 == 贷方合计），确保功能迭代不回归。
