# 记账规则、幂等与结算/对账语义

## 1. 会计模型

系统是**单一法人账簿**（支付机构/电子钱包运营方视角）。用户钱包余额是运营方对用户的**负债**，
用户充值对应的资金是运营方的**备付金资产**。所有资金运动都以**复式记账凭证**记录，
每张凭证必须借贷平衡。

### 1.1 账户类型与正常余额方向

| 类型 | 正常余额方向 | 例子 |
| --- | --- | --- |
| ASSET 资产 | 借方 | `FLOAT_CASH`（备付金）、`RECON_SUSPENSE_REC`（对账暂记应收） |
| LIABILITY 负债 | 贷方 | 用户/商户钱包、`PAYABLE_MERCHANT:<商户>`（待结算款）、`RECON_SUSPENSE`（暂记应付） |
| INCOME 收入 | 贷方 | `FEE_INCOME`（手续费收入） |
| EXPENSE 费用 | 借方 | （预留） |
| EQUITY 权益 | 贷方 | （预留） |

账户余额始终保存为**正常余额方向上的非负净值**。过账时的余额约束：

- 借方正常账户：本凭证的**贷方发生额** ≤ 当前余额；
- 贷方正常账户：本凭证的**借方发生额** ≤ 当前余额。

这比"余额不能出现反方向"更通用：既阻止资产/钱包透支，也允许负债账户之间合法的
"借 A 贷 B"划转（如两个钱包间转账：借 转出方钱包 / 贷 转入方钱包）。

### 1.2 业务分录

**入金（充值）** `INITIAL_DEPOSIT`

```
借 FLOAT_CASH            （备付金资产增加）
  贷 <用户钱包>           （钱包负债增加）
```

**支付受理** `PAYMENT`（资金不直接进商户钱包，先进待结算负债）

```
借 <付款方钱包>           （负债减少）
  贷 PAYABLE_MERCHANT:<商户> （待结算负债增加）
```

**退款** `REFUND`（按原支付当前状态选择出账科目，与账上资金位置对齐）

```
支付未结算（钱还在待结算负债）：
借 PAYABLE_MERCHANT:<商户>  （待结算负债减少）
  贷 <付款方钱包>           （钱包负债增加，退回给付款人）

支付已结算（钱已到商户钱包）：
借 <商户钱包>               （商户负债减少）
  贷 <付款方钱包>           （钱包负债增加，退回给付款人）
```

**批次结算** `SETTLEMENT`（待结算款结入商户钱包，按商户汇总成一张凭证）

```
借 PAYABLE_MERCHANT:<商户A>  （待结算负债减少）
  贷 <商户A钱包>             （商户负债增加）
借 PAYABLE_MERCHANT:<商户B>
  贷 <商户B钱包>
  ...
```

**批次手续费** `SETTLEMENT_FEE`（独立凭证，逐商户扣收，贷记手续费收入）

```
借 <商户A钱包>  feeA
借 <商户B钱包>  feeB
  贷 FEE_INCOME  feeA + feeB
```

手续费口径：`fee_i = floor(amount_i × BPS / 10000)`，**逐笔计算后汇总**
（默认 BPS=60，即 0.60%）。建批时按（原金额 − 已退款金额）预估批次毛额/手续费/净额，
**结算时按结算时刻的最新已退金额重新核定**（见第 4 节）；手续费不退还，
已结算支付的退款全额从商户钱包扣减，商户钱包不足时退款失败（`INSUFFICIENT_FUNDS`）。

**对账自动调整** `RECON_ADJUSTMENT`（见第 5 节）。

### 1.3 原子性

- 所有写操作通过 `storage.Store.Update(func(tx *Tx) error)` 在**同一个互斥临界区**内完成；
  回滚模型：`Update` 先对全部数据表做快照，回调在快照上读写，**返回错误则快照直接丢弃**，
  本次改动（包括已写入的 IN_FLIGHT 幂等记录）对外界完全不可见。
- 支付受理/退款在同一临界区内完成"幂等记录写入 + 凭证过账 + 业务单写入 + 幂等记录置 DONE"，
  因此不可能出现只扣款不入账、或退了一半账对不上的半截状态。
- 凭证按业务键 `(BizType, BizID)` 唯一：`postInTx` 发现重复业务键时直接返回原凭证，
  这是记账引擎自身的第二道幂等防线。

## 2. 支付受理与幂等语义

幂等记录两状态：`IN_FLIGHT` → `DONE`，记录请求指纹
`(付款方, 收款方, 金额, 币种, 附言)`。

| 到达情形 | 处理 |
| --- | --- |
| 无记录 | 写入 IN_FLIGHT → 原子过账与建支付单 → 置 DONE，返回新支付单 |
| 有 DONE 记录且**指纹相同** | 直接返回首次支付单，`Replayed=true`，**不过账、不扣款** |
| 有 DONE/IN_FLIGHT 记录且**指纹不同** | 返回 `IDEMPOTENCY_CONFLICT`，明确拒绝（错误信息携带既有内容与本次内容） |
| 相同键**并发**到达 | 临界区串行化：胜者完成受理；败者看到 IN_FLIGHT，返回 `IDEMPOTENCY_CONFLICT`，调用方稍后以**相同请求**重试即可拿到幂等结果 |

设计要点：

- 幂等键必填；缺键、金额非正、同账户收付等参数问题返回 `INVALID_ARGUMENT`；
- 账户不存在 / 币种不一致 / 余额不足分别返回 `ACCOUNT_NOT_FOUND` /
  `CURRENCY_MISMATCH` / `INSUFFICIENT_FUNDS`，失败原因可区分；
- 失败受理不会产生凭证，账户余额与试算平衡保持不变；
- **失败不占用幂等键**：因余额不足等明确原因失败时整个临界区回滚，
  IN_FLIGHT 记录一并丢弃。之后用同键同内容重试会得到与首次相同的失败结论
  （结论稳定、原因明确）；待条件具备（如充值后）同一键还可正常走通，
  换新幂等键发起也不受任何影响。

## 3. 退款语义

退款针对**已受理成功**的支付（未结算或已结算均可），支持全额与多次部分退款。

### 3.1 退款幂等

与支付受理共用同一套幂等机制（IN_FLIGHT/DONE + 请求指纹），
退款指纹为 `(原支付号, 金额, 币种, 原因)`，业务类型标记为 `REFUND`：

| 到达情形 | 处理 |
| --- | --- |
| 无记录 | 写入 IN_FLIGHT → 原子过账与建退款单 → 置 DONE，返回新退款单 |
| 有 DONE 记录且指纹相同 | 返回首次退款单，`Replayed=true`，**不退第二次** |
| 有记录且指纹不同 | `IDEMPOTENCY_CONFLICT`，明确拒绝 |
| 相同键并发到达 | 临界区串行化，后到者见 IN_FLIGHT 返回冲突，稍后以相同请求重试 |

### 3.2 失败分类与重试稳定性

| 失败原因 | 错误码 |
| --- | --- |
| 原支付不存在 | `PAYMENT_NOT_FOUND` |
| 退款金额非正 / 参数缺失 | `INVALID_ARGUMENT` |
| 累计退款超过可退余额（原额 − 已退） | `REFUND_EXCEEDS_REMAINING` |
| 请求币种与原支付币种不一致 | `CURRENCY_MISMATCH` |
| 付款人/商户账户不存在 | `ACCOUNT_NOT_FOUND` |
| 已结算支付退款时商户钱包余额不足 | `INSUFFICIENT_FUNDS` |

任何失败都在同一临界区内整体回滚：**凭证、退款单、支付累计退款额、幂等记录
一个都不落**。因此失败的重试语义与支付受理一致：同键同内容重试结论稳定、
原因明确；失败不污染幂等键，修正内容后（同键或新键）可正常发起。

### 3.3 累计上限与并发

支付单上维护 `RefundedAmount`（已累计退款额），可退余额 = 原额 − 已退。
每次退款在同一临界区内"检查可退余额 → 过账 → 累计"，并发退款被串行化：
不超退、不丢更新，任意时刻可退余额都是准确的。

### 3.4 与结算/对账的先后关系

- **未结算退款**：资金出自 `PAYABLE_MERCHANT`（退款冲减待结算款）。
  支付已进待结算批次但未结算时发生退款，之后结算该批次，
  结算金额 = 原额 − 已退（手续费同口径），**已退还给用户的钱不会再结给商户**；
  全部退完的支付不再产生结算分录，仅随批次置为 `SETTLED`。
- **已结算退款**：资金出自商户钱包（手续费不退）。商户钱包不足时退款失败，
  原因明确为 `INSUFFICIENT_FUNDS`，且一分钱不动。
- **对账兼容**：对账把批次内支付的退款单一并加载，对账单中 `TxnID` 等于退款号的
  记录按退款核对（差异对象标记 `Subject=REFUND`），不会被误判为"内部缺失"的
  幽灵记录；内部有、对账单没有的退款记 `MISSING_IN_STATEMENT(REFUND)` 挂人工。
  退款发生前已跑出的对账结果不受影响（对账按批次幂等，结果落库不重算）。
- 重复结算、重复对账、重复退款均幂等：不重复过账、不多出调整凭证。

## 4. 结算语义

1. **建批 `CreateBatch`**：批次单一币种；所有支付必须存在、币种一致、状态为
   `PENDING_SETTLEMENT` 且未归属过批次（防止重复打包）。批次按（原金额 − 已退款金额）
   预估毛额、手续费、净额并保存支付清单，把支付的 `SettlementBatchID` 指向批次。
2. **结算 `SettleBatch`**：按结算时刻口径重新核定每笔实际结算金额
   （原金额 − 最新已退款金额）与手续费，在一个临界区内过"结算凭证 + 手续费凭证"
   两张平衡凭证，批次毛额/手续费/净额更新为实际口径；随后批次置 `SETTLED`、
   批次内支付全部置 `SETTLED`。任一步失败整体回滚。
3. **结算幂等**：对已 `SETTLED` 批次再次调用，直接返回既有批次，不重复过账、不重复扣费。

商户最终到账净额 = （毛额 − 已退款）− 手续费；结算后其 `PAYABLE_MERCHANT`
账户中未被退款冲减的部分归零。

## 5. 对账语义

输入：已结算批次 + 对账单记录（`TxnID` 对齐内部支付号或退款号；来源可为内存构造
或本地 CSV，无网络依赖）。批次内支付的退款单一并纳入对账口径，
差异记录用 `Subject` 字段区分对象（`PAYMENT` / `REFUND`）。

### 5.1 差异分类

| 差异类型 | 判定 | 处理 |
| --- | --- | --- |
| `MISSING_IN_STATEMENT` | 内部有已结算支付/退款，对账单完全没有 | **不自动调整**，登记差异挂人工核查 |
| `MISSING_IN_INTERNAL` | 对账单有 `TxnID`，内部无此支付也无此退款 | 自动调整：借 FLOAT_CASH / 贷 RECON_SUSPENSE（应付暂记） |
| `AMOUNT_MISMATCH` | 双方都有（支付对支付、退款对退款）但金额不等 | 按差额自动调整（见下） |
| `DUPLICATE_RECORD` | 对账单中同一 `TxnID` 出现多次 | 第一条参与匹配，多出的条目登记为重复，**不自动调整** |

退款记录的识别：对账单 `TxnID` 命中内部退款号即按退款核对（`Subject=REFUND`），
金额一致即匹配；不一致按差额自动挂暂记；内部有退款而对账单缺失记
`MISSING_IN_STATEMENT(REFUND)`。退款记录**不会**被当成 `MISSING_IN_INTERNAL`
幽灵记录，重复执行也不会被重复登记。

金额不符的差额调整（`delta = 对账单金额 − 内部金额`）：

```
delta > 0（渠道多收）：借 FLOAT_CASH delta / 贷 RECON_SUSPENSE delta
delta < 0（渠道少收）：借 RECON_SUSPENSE_REC |delta| / 贷 FLOAT_CASH |delta|
```

使用**两个方向不同的暂记科目**（负债/资产），保证自动调整凭证本身也满足
"账户余额不得为负"的约束。自动调整只触碰系统科目（备付金、暂记），
**不直接改客户与商户账**；单边缺失（对账单侧）与重复记录只登记不调整，留给人工。

### 5.2 对账幂等

对账结果以 `BatchID` 为键持久化。对同一批次再次执行 `Reconcile` 时**直接返回首次运行
结果**，不会重新匹配、不会生成第二张调整凭证、暂记科目余额不变。
调整凭证的业务键为 `RECON:<TxnID>:MISMATCH` / `RECON:<TxnID>:MISSING_INTERNAL`，
即使绕过批次幂等也会被记账引擎的业务键唯一约束挡住。

## 6. 并发与一致性说明

- 内存存储用一把互斥锁把每个 `Update` 临界区串行化，等价于数据库的可串行化事务；
  `View` 提供一致读。生产环境替换为数据库时，对应到行锁/乐观版本号
  （账户上有 `Version` 字段）即可，领域语义不变。
- 并发划转测试验证两件事：高并发下（1）总成功笔数与双方余额严格守恒、不丢更新；
  （2）余额只够部分请求时成功笔数恰为 `初始余额/单笔金额`，余额绝不为负。
- 并发退款测试验证：同一笔支付上 20 个并发退款请求（各退 1/10 原额），
  恰好 10 笔成功、10 笔因 `REFUND_EXCEEDS_REMAINING` 拒绝，累计退款精确等于原额，
  不超退、不丢更新。

## 7. 验证方法

```bash
go test -race -count=3 ./...      # 全量、竞态检测、重复 3 次
go test ./internal/refund/ -v     # 退款专项：累计上限/并发/两种资金来源/失败重试
go run ./cmd/demo                 # 端到端演示（含退款 → 再结算 → 再对账）
```

测试日志会打印幂等键/交易号以及判定依据，例如：

- `幂等键 key-replay 判定依据: 三次提交均返回支付号 pay-...，余额保持 ...（仅扣一次）`
- `幂等键=rfnd-idem-1 首次退款号=rfnd-... 重放退款号=rfnd-... Replayed=true`
- `并发退款汇总: 成功=10 超退拒绝=10 判定依据=可退余额不足即拒`
- `失败重试稳定: 幂等键=rfnd-retry-1 两次均判定=REFUND_EXCEEDS_REMAINING（失败未占用该键）`
- `批次=... 毛额=20000 手续费=120 净额=19880 判定依据=结算金额=原额-已退`
- `批次 batch-... 重复对账判定依据: 复用首次运行结果，调整凭证仍为 jrn-...，暂记余额保持 ...`

每个正常路径用例结束时都做试算平衡断言（借方合计 == 贷方合计），确保功能迭代不回归。
